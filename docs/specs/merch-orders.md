## 0. Что сломано сегодня

В `components/promo/MerchMockups.tsx:28` живёт константа:

```ts
const PRINTFUL_GENERATOR_URL = 'https://www.printful.com/dashboard'
```

и кнопка «Открыть в Printful» (`:124-133`, ключ `merch.openPrintful`). Это тупик по определению. Человек, который собрал узор и захотел футболку, не имеет кабинета Printful и никогда не заведёт его ради одной футболки. Кнопка ведёт на чужой логин, за которым его ждёт форма создания магазина. Конверсия такого пути равна нулю не «низкая», а буквально нулевая.

Printful Quick Stores (готовая витрина от Printful) не спасают: они доступны только продавцам в США и не имеют API, то есть ни узор туда программно не положить, ни ссылку на конкретный товар не выдать.

Значит правильная схема ровно одна: **покупка происходит у нас**. Мы показываем товар с узором и цену, человек жмёт «Купить», платит нашей кассой Stripe (там же оставляет адрес доставки), а Printful узнаёт о заказе от нашего сервера через API и печатает. Printful остаётся подрядчиком печати, а не витриной. Покупатель про Printful вообще может не знать до письма с трек-номером.

Что уже есть и переиспользуется без изменений:

| Что | Где | Роль в новой схеме |
|---|---|---|
| Каталожные id товаров и областей печати | `lib/promo/printfulCatalog.ts` | база для варианта заказа и позиции макета |
| HTTP-обвязка Printful (заголовки, таймаут, коды ошибок) | `lib/promo/printful.ts:71-104` | переиспользуем `printfulHeaders` и `errorFromStatus` |
| Публикация макета по https-ссылке для Printful | `lib/promo/storage.ts` | тот же приём, другой bucket и другой TTL (см. §3.3) |
| Рендер доски в картинку | `lib/export` (`renderBoardSvg`), `sharp` уже в зависимостях | print-файл рисуется тем же рендером |
| Checkout через голый REST Stripe | `app/actions/credits.ts:27-65` | шаблон для `createMerchCheckoutAction` |
| Разбор разового платежа | `lib/stripe/oneTime.ts` | добавляется вид `merch` |
| Вебхук с ветками по `metadata.kind` | `app/api/stripe/webhook/route.ts:33-149` | добавляется ветка `merch` |

## 1. Ассортимент v1

Товары те же четыре, что уже показываются в мокапах (`lib/promo/types.ts:152`): футболка, кружка, постер, фартук. Никаких новых позиций: каждая новая позиция это новый print-файл, новая область печати и новая строка себестоимости, а продавать нужно начать с одной.

Каталожные координаты уже сверены с живым Printful 12.08.2026 и лежат в `lib/promo/printfulCatalog.ts`. Для заказа их не хватает: там ровно один вариант на товар (у футболки это M White), а продавать футболку одного размера нельзя.

### 1.1 Таблица вариантов

Новый файл `lib/merch/catalog.ts`. Он расширяет `PRINTFUL_PLACEMENTS`, а не заменяет его: генератору мокапов по-прежнему хватает одного «показательного» варианта, а заказу нужен весь ряд размеров.

| Товар | Printful product | Вариант | variant_id | Размер печати |
|---|---|---|---|---|
| Футболка S | 71 Unisex Staple T-Shirt (Bella+Canvas 3001), White | S | 4011 | 1800x2400 px, front |
| Футболка M | 71 | M | 4012 | то же |
| Футболка L | 71 | L | 4013 | то же |
| Футболка XL | 71 | XL | 4014 | то же |
| Кружка | 19 White Glossy Mug | 11 oz | 1320 | 2700x1050 px, default |
| Постер | 1 Enhanced Matte Paper Poster (in) | 18x24 in | 1 | 5400x7200 px, default |
| Фартук | 894 All-Over Print Apron | one size | 22903 | 4350x4783 px, front |

Три из семи id уже проверены на живом API (4012, 1320, 1, 22903 стоят в `printfulCatalog.ts` и по ним реально рисовались мокапы). Три остальных (4011, 4013, 4014) взяты по порядку ряда размеров того же товара и **обязаны быть подтверждены до релиза** скриптом из §1.2. Слепо верить порядку нельзя: в этом же проекте уже был случай, когда id 186 числился фартуком, а оказался носками (комментарий в `printfulCatalog.ts:8`).

Цвет футболки в v1 один, белый. Причина не эстетическая: каждый цвет это отдельный ряд variant_id, отдельная себестоимость и отдельный мокап, а узор доски на белом читается лучше всего. 2XL не берём: у Printful он дороже остальных размеров, и это единственная позиция, которая ломает «одна цена на все размеры» (см. §2.3).

### 1.2 Скрипт сверки каталога

`scripts/printful-catalog.ts`, запуск `pnpm tsx scripts/printful-catalog.ts` с `PRINTFUL_API_KEY` и `PRINTFUL_STORE_ID` в окружении. Делает `GET /products/{id}` по каждому из четырёх товаров и печатает таблицу: variant_id, name, size, color, price. Ничего не пишет в репозиторий сам, только показывает. Человек сверяет глазами и правит `lib/merch/catalog.ts` руками.

Скрипт нужен по двум поводам: подтвердить id размеров и снять актуальную себестоимость (§2.2). Гонять его в CI не надо, это ручной инструмент раз в квартал.

## 2. Ценообразование

### 2.1 Формула

```
retail = round99(cost_variant * MERCH_MARGIN + cost_shipping)
```

- `cost_variant` - что Printful списывает с нас за печать единицы товара, в центах. Снимок из каталога, см. §2.2.
- `cost_shipping` - что Printful списывает за доставку одной единицы этого товара, в центах. Худшая ставка по разрешённым странам, тоже снимок.
- `MERCH_MARGIN` - множитель наценки, env, дефолт `1.8`. Живёт в `lib/merch/pricing.ts`, читается один раз на модуль, как остальные env проекта.
- `round99` - округление вверх до ближайшего значения, оканчивающегося на `.99`.

```ts
/** Округление вверх до ближайшей цены вида X.99. 2431 -> 2499, 2499 -> 2499, 2500 -> 2599. */
export function round99(cents: number): number {
  return Math.ceil((cents - 99) / 100) * 100 + 99
}
```

Наценка применяется только к печати, доставка добавляется по себестоимости уже после умножения. Иначе на постере (доставка дорогая) наценка на доставку сама по себе превысила бы наценку на товар, и цена уехала бы в неприличное.

Валюта одна, USD. Она же у всех остальных платежей проекта, и `parseOneTimeEvent` отбивает всё, что не `usd` (`lib/stripe/oneTime.ts:77-78`). Отображение цены человеку с русской локалью тоже в долларах: врать «₽» при списании в долларах хуже, чем показать доллар.

### 2.2 Откуда берётся себестоимость

Себестоимость **не спрашивается у Printful в рантайме**. Она лежит снимком в `lib/merch/catalog.ts` рядом с variant_id:

```ts
export interface MerchVariant {
  readonly productId: MerchProductId
  readonly size: MerchSize          // 's' | 'm' | 'l' | 'xl' | 'one'
  readonly variantId: number
  /** Снимок цены Printful за печать, центы. Сверено скриптом §1.2, дата в комментарии. */
  readonly costCents: number
  /** Снимок худшей ставки доставки по allowed_countries, центы. */
  readonly shipCents: number
}
```

Три довода против живого запроса цены на каждый рендер карточки:

1. **Скорость.** Карточка товара обязана показать цену мгновенно, а `GET /products/{id}` это 200-600 мс сетевого похода в чужой API. Четыре товара это четыре похода на каждый заход во вкладку «Промо».
2. **Лимиты.** Printful режет нас по частоте уже сегодня: генератор мокапов пускает две задачи в минуту (замер в `lib/promo/printful.ts:41-44`). Дёргать их каталог на каждый рендер значит добровольно жить у границы 429.
3. **Детерминизм.** Цена, которую человек увидел, и цена, которую он заплатил, обязаны совпасть. Живой запрос это два разных ответа в двух разных секундах и потенциальный спор.

Риск снимка честный: Printful поднял цены, а мы продаём по старым и съедаем маржу. Лечится дисциплиной, а не кодом: скрипт §1.2 раз в квартал, и разница видна на глаз. При марже 1.8 подорожание печати на 10% съедает около 12% маржи, а не выводит сделку в минус, так что это терпимо для v1.

**В момент создания заказа снимок фиксируется в строке заказа** (`cost_cents`, `retail_cents`, `margin`). Заказ, оплаченный вчера, не переоценивается сегодняшним снимком никогда.

### 2.3 Одна цена на все размеры футболки

У Printful S-XL стоят одинаково, различается только 2XL и выше. Раз 2XL в v1 нет, цена футболки одна для всех размеров. Это упрощает всё: карточка показывает одно число до выбора размера, и выбор размера не меняет сумму под кнопкой.

Если позже добавится 2XL, `costCents` у него будет свой, и карточка обязана будет показывать «от $X» до выбора размера. Это уже v2.

### 2.4 Доставка: фиксированная ставка, вшитая в цену

**Решение: доставка включена в цену товара, в Stripe Checkout уходит единственная ставка `fixed_amount = 0` с подписью «Доставка включена».** Адрес при этом собирается полноценно, он нужен Printful.

Почему не живой расчёт через `POST /shipping/rates` у Printful: расчёт требует адрес, а адрес человек вводит уже внутри Checkout, на странице Stripe. Пересчитать сумму после ввода адреса hosted Checkout не умеет вовсе - для этого нужен собственный флоу на Payment Element с серверным пересчётом. Это отдельная витрина оплаты вместо одной ссылки, то есть в разы больше кода и больше мест, где касса может сломаться. Ради товара, который пока никто не купил, это неоправданно.

Почему не разные ставки по регионам через `shipping_options`: hosted Checkout показывает **один и тот же список ставок всем**, отфильтровать его по стране покупателя нельзя. Получилось бы либо «выберите зону сами» (человек выберет дешёвую), либо одна ставка для всех, что равнозначно вшитой в цену, но с лишним экраном.

Почему вшить лучше, чем «одна ставка $9.90 сверху»: цена на карточке равна цене в чеке. Никаких «$24.99, ой, теперь $34.89» на последнем шаге - самый надёжный способ потерять покупателя.

`cost_shipping` берём как **худшую** ставку по списку разрешённых стран из §2.5. Считать её надо один раз руками: сделать в кабинете Printful тестовый расчёт на адрес в Австралии (дальше всех от их фабрик) и записать число. На американских и европейских адресах мы просто заработаем чуть больше.

### 2.5 Куда доставляем

`shipping_address_collection[allowed_countries]` заполняется явным списком. v1:

`US, CA, GB, DE, FR, ES, IT, NL, PL, SE, IE, PT, AT, BE, DK, FI, CZ, AU, NZ, JP`

Печатать некуда не значит «весь мир»: у Printful есть страны, куда доставки нет вовсе, и заказ туда упадёт уже после списания денег.

**Россия в список не входит.** Printful в РФ не отправляет. Это не наше решение и не то, что можно обойти кодом, и продукт с русским интерфейсом обязан сказать об этом честно, до кнопки: под ценой строка «Доставка: США, Канада, Великобритания, ЕС, Австралия, Япония. В Россию и Беларусь Printful не отправляет». Молча принять деньги и потом развести руками нельзя.

### 2.6 Пример расчёта

Иллюстрация, не источник истины (реальные числа снимет скрипт §1.2):

| Товар | Печать | Доставка | retail при 1.8 |
|---|---|---|---|
| Футболка | $9.50 | $4.70 | round99(1710 + 470) = **$21.99** |
| Кружка | $7.95 | $6.90 | round99(1431 + 690) = **$21.99** |
| Постер 18x24 | $12.50 | $7.95 | round99(2250 + 795) = **$30.99** |
| Фартук | $19.95 | $5.60 | round99(3591 + 560) = **$41.99** |

## 3. Print-файл

### 3.1 Почему нельзя взять файл мокапа

Мокап собирается из `boardPngDataUrl(model)` с `REFERENCE_PX = 1024` (`components/promo/boardPng.ts`). Тысяча пикселей на квадрат это ровно то, что нужно картинке в браузере, и категорически мало для печати: на постере 18x24 дюйма это 57 dpi, то есть видимые квадратики вместо шашки. Printful формально примет файл и напечатает мыло, а претензия прилетит нам.

Значит print-файл рисуется отдельно и **на сервере**, а не в браузере.

### 3.2 Как рисуется

Новый модуль `lib/merch/print.ts`:

```ts
/** Сторона квадратного print-файла по товару, px. Равна меньшей стороне области печати, но не больше потолка. */
export function printSidePx(id: MerchProductId): number
```

Логика: берём `PRINTFUL_PLACEMENTS[id]`, считаем `min(areaWidthPx, areaHeightPx)` - это сторона того самого центрированного квадрата, который уже вычисляет `centeredSquare` для мокапов. Ограничиваем потолком `MERCH_PRINT_MAX_PX = 4000`, чтобы файл постера не раздувался в десятки мегабайт.

| Товар | Квадрат области | Сторона файла | Итоговый dpi |
|---|---|---|---|
| Футболка | 1800 | 1800 | 150 |
| Кружка | 1050 | 1050 | 300 |
| Постер | 5400 | 4000 | ~222 |
| Фартук | 4350 | 4000 | ~138 |

222 dpi на постере и 138 на фартуке ниже «идеальных» 300, но узор доски это крупные плашки заливки без мелких деталей и без текста: артефактов на такой картинке физически неоткуда взяться. Printful предупреждает ниже 150 dpi, но печатает.

Рендер: `renderBoardSvg(model, { maxPx: side })` даёт SVG, `sharp(Buffer.from(svg)).png()` даёт PNG. `sharp` уже в зависимостях и уже используется на сервере (`lib/promo/crop.ts`), новых пакетов не нужно.

Позиция макета внутри области печати берётся у существующей `centeredSquare` из `lib/promo/printfulCatalog.ts` без изменений: заказ и мокап обязаны показывать одно и то же расположение, иначе человек купит одно, а получит другое.

### 3.3 Где живёт файл

Новый bucket `merch-prints`, отдельной миграцией, по образцу `promo-mockups` (`20260812150000_promo_mockups_bucket.sql`):

- **public на чтение**, потому что Printful забирает файл обычным GET со своей стороны и никакой авторизации не поддерживает. Имя объекта случайное и неугадываемое, как в `artworkPath` (`lib/promo/storage.ts:30-33`).
- Путь: `{user_id или anon}/{orderId}.png`. Привязка к заказу, а не ко времени: файл должен переживать ровно столько, сколько живёт заказ.
- **TTL 90 дней**, а не 60 минут как у мокапов. Причина ключевая: заказ создаётся черновиком с `confirm=false`, и Printful заберёт файл не в момент создания, а в момент подтверждения, которое может случиться через сутки. Снести файл сразу после создания заказа значит гарантированно получить у Printful «file failed to download».
- Уборка: функция `purge_merch_prints()` в той же миграции, по образцу `purge_promo_mockups`, сносит объекты старше 90 дней. Вызывается тем же способом, что и уборка промо (крон на Hobby суточный, этого хватает).

Метод передачи файла Printful: **URL, а не Files API**. `POST /orders` принимает `files[].url` и скачивает сам. Загрузка через `POST /files` дала бы file_id и переживание нашего bucket, но это лишний сетевой раунд и лишняя точка отказа в вебхуке, где каждая секунда на счету. Наш Storage не менее надёжен, чем их файловое хранилище.

### 3.4 Когда рисуется

В момент нажатия «Купить», до создания Checkout Session, синхронно в server action. Не в вебхуке.

Довод: если рендер упал, человек ещё не заплатил, и мы просто показываем ошибку «не получилось подготовить макет, попробуйте ещё раз». Если бы рендер жил в вебхуке, его падение означало бы списанные деньги и заказ, который некому напечатать. Всё, что может упасть, должно падать до кассы.

Цена этого решения: файлы брошенных корзин. Человек нажал «Купить», ушёл со страницы Stripe, файл остался. Это несколько сотен килобайт, которые снесёт уборка через 90 дней. Приемлемо.

## 4. Поток покупки

```
[карточка товара]  Купить -> (футболка: модалка размера)
        |
        v
createMerchCheckoutAction({ productId, size, projectId, boardPng? })
        | 1. проверки: касса жива, Printful настроен, пользователь залогинен
        | 2. цена из снимка каталога
        | 3. рендер print-файла (sharp), заливка в merch-prints
        | 4. insert merch_orders (status = pending_payment)  <- id заказа рождается здесь
        | 5. POST /v1/checkout/sessions, metadata[kind]=merch, metadata[merch_order_id]=<id>
        | 6. update merch_orders.stripe_session_id
        v
[hosted Checkout Stripe: карта + адрес доставки]
        |
        v (checkout.session.completed)
POST /api/stripe/webhook
        | a. parseOneTimeEvent -> kind 'merch'
        | b. читаем merch_orders по merch_order_id, сверяем user_id и сумму
        | c. status pending_payment -> paid, пишем адрес и контакты
        | d. POST https://api.printful.com/orders?confirm=false, external_id = order.id
        | e. status paid -> draft_created, пишем printful_order_id
        v
[/account/orders: «Оплачено, готовим к печати»]
```

### 4.1 Server action `createMerchCheckoutAction`

Файл `app/actions/merch.ts`. Форма ответа по образцу `PackCheckoutResult` (`app/actions/credits.ts:11-12`):

```ts
export type MerchCheckoutError =
  | 'invalid'          // не прошла схема zod
  | 'disabled'         // нет ключей Stripe или Printful
  | 'unauthenticated'  // нужен вход
  | 'render'           // не собрался print-файл
  | 'storage'          // не залился в bucket
  | 'failed'           // Stripe не ответил
export type MerchCheckoutResult =
  | { readonly ok: true; readonly url: string }
  | { readonly ok: false; readonly error: MerchCheckoutError }
```

Схема входа в `lib/merch/schema.ts` (не в `lib/promo/schema.ts`: мерч-заказ это свой домен):

```ts
export const merchOrderSchema = z.object({
  product: z.enum(['tshirt', 'mug', 'poster', 'apron']),
  size: z.enum(['s', 'm', 'l', 'xl', 'one']),
  projectId: z.uuid().nullable(),
  design: designSchema,   // тот же документ доски, что уходит в сохранение проекта
})
```

Дизайн приходит документом, а не PNG. Это отличается от мокапов, где на сервер летит `boardPng` в base64 (`merchSchema`, `lib/promo/schema.ts:87`), и отличается сознательно: print-файл должен рисоваться сервером в высоком разрешении, а гнать 4000-пиксельный PNG из браузера в server action невозможно (`MAX_PNG_CHARS = 3_500_000`, то есть около 2.6 МБ, и это лимит не с потолка, а из ограничений тела server action). Документ доски весит килобайты, а рендер из него на сервере даёт любое разрешение.

Пары «товар + размер» валидируются не только схемой: `mug/poster/apron` принимают только `size = 'one'`, футболка только `s|m|l|xl`. Неверная пара это `invalid`, не молчаливая подмена.

**Требование логина.** Покупка без аккаунта технически возможна (Stripe соберёт email), но тогда «Мои заказы» показать некому и статус человек не увидит нигде, кроме письма. Поэтому v1 требует входа: `getCurrentUser()`, при `null` возвращаем `unauthenticated`, а UI показывает то же приглашение войти, что и «Сохранить проект».

**Pro-гейта нет.** `assertAiAllowed` тут не зовётся. Мокапы это наш расход (квота на AI), а покупка мерча это наша выручка. Запирать выручку за подпиской абсурдно.

**Rate limit.** Пере­использовать `passRateLimit` из промо не нужно: каждая покупка упирается в реальную карту. Достаточно защиты от дурака: не больше 10 незавершённых `pending_payment` заказов на пользователя за час, проверка запросом к своей же таблице. Превышение это `failed` с логом.

### 4.3 Тело заказа Printful

`lib/merch/printfulOrder.ts`, чистая функция сборки тела плюс тонкая обёртка над `fetch` (та же схема разделения, что в `lib/promo/printful.ts`: сеть за параметром `fetchImpl`, разбор в чистых функциях, тест без единого байта наружу).

```ts
export function orderBody(input: MerchOrderInput): PrintfulOrderBody {
  const place = PRINTFUL_PLACEMENTS[input.product]
  return {
    external_id: input.orderId,       // ключ идемпотентности, см. §6.4
    shipping: 'STANDARD',
    recipient: {
      name: input.recipientName,
      address1: input.address1,
      address2: input.address2 ?? undefined,
      city: input.city,
      state_code: input.stateCode ?? undefined,
      country_code: input.countryCode,
      zip: input.zip,
      email: input.email,
      phone: input.phone ?? undefined,
    },
    items: [{
      variant_id: input.variantId,
      quantity: 1,
      retail_price: (input.retailCents / 100).toFixed(2),
      files: [{
        type: place.placement,        // 'front' у одежды, 'default' у кружки и постера
        url: input.printFileUrl,
        position: centeredSquare(place),
      }],
    }],
    retail_costs: { currency: 'usd', subtotal: (input.retailCents / 100).toFixed(2), shipping: '0.00' },
  }
}
```

Запрос: `POST https://api.printful.com/orders?confirm=false`, заголовки из существующей `printfulHeaders({ apiKey, storeId })`, таймаут `PRINTFUL_TIMEOUT_MS` (15 с) оттуда же.

**`confirm=false` обязателен в v1.** Заказ создаётся черновиком: Printful его видит, но не печатает и не списывает деньги, пока владелец не нажмёт «Confirm» в кабинете. Это даёт три вещи разом: тестовые заказы не жгут баланс, первые живые заказы проходят через глаза человека, и любая ошибка в позиционировании макета ловится до печати, а не после.

Флаг вынесен в env `PRINTFUL_CONFIRM_ORDERS` (дефолт `false`). Когда доверие к потоку появится, значение меняется на `true` без деплоя кода, и заказы уходят в печать автоматически.

`state_code` обязателен для США, Канады и Австралии и запрещён для большинства прочих стран. Stripe отдаёт его в `address.state`. Правило простое: передавать, если пришёл непустой, и не передавать иначе. Printful на лишний `state_code` отвечает 400, поэтому `undefined`, а не пустая строка.

### 5.2 Статусы

| Статус | Кто ставит | Что значит | Что видит человек |
|---|---|---|---|
| `pending_payment` | server action при создании | сессия создана, деньги не пришли | заказа в списке нет вовсе |
| `paid` | вебхук, шаг (c) | деньги у нас, Printful ещё не знает | «Оплачено, оформляем печать» |
| `draft_created` | вебхук, шаг (e) | Printful принял черновик | «Оплачено, готовим к печати» |
| `failed` | вебхук после исчерпания попыток | деньги у нас, печати не будет | «Что-то пошло не так, мы уже разбираемся» |
| `cancelled` | вручную владельцем | заказ отменён, деньги возвращены | «Отменён, деньги возвращены» |

`pending_payment` намеренно не показывается в «Моих заказах». Строка в этом статусе означает всего лишь «человек нажал Купить», и половина таких строк это брошенные корзины. Показывать их значит пугать человека несуществующими долгами.

Отдельного статуса «отправлен» в v1 нет: чтобы его знать, нужен вебхук от Printful, а его в v1 не делаем (§11).

## 6. Вебхук checkout.session.completed

### 6.1 Разбор события

В `lib/stripe/oneTime.ts` добавляется вид:

```ts
export type OneTimeKind = 'wallet_topup' | 'gallery_purchase' | 'pro_pass' | 'ai_pack' | 'merch'
```

и в `sessionSchema.metadata` поле `merch_order_id: z.string().optional()`, а в `OneTimePayment` соответственно `merchOrderId: string | null`. Все существующие инварианты (`mode = payment`, `payment_status = paid`, валюта `usd`, целое положительное `amount_total`, обязательный `supabase_user_id`) остаются как есть и распространяются на мерч без изменений.

**Адрес доставки** живёт не в metadata, а в самом объекте сессии. Тут единственная тонкость этого раздела: в разных версиях Stripe API адрес лежит по разным путям. В старых это `session.shipping_details`, в новых `session.collected_information.shipping_details`. Схема обязана принимать оба и брать первый непустой:

```ts
const shippingDetailsSchema = z.object({
  name: z.string().nullish(),
  address: z.object({
    line1: z.string().nullish(),
    line2: z.string().nullish(),
    city: z.string().nullish(),
    state: z.string().nullish(),
    postal_code: z.string().nullish(),
    country: z.string().nullish(),
  }).nullish(),
}).nullish()

// в sessionSchema:
shipping_details: shippingDetailsSchema,
collected_information: z.object({ shipping_details: shippingDetailsSchema }).nullish(),
customer_details: z.object({
  email: z.string().nullish(),
  phone: z.string().nullish(),
  name: z.string().nullish(),
}).nullish(),
```

Это ровно то место, где интеграция ломается тихо: схема не упадёт, адрес окажется пустым, и Printful вернёт 400 уже после списания денег. Поэтому проверка адреса это отдельный явный шаг (§6.3), а не `?? ''` где-то в глубине.

### 6.2 Ветка в роуте

В `handleOneTime` добавляется ветка `payment.kind === 'merch'` до общего `wallet_topup`. Порядок шагов внутри жёсткий, и он весь про «не потерять деньги»:

```
1. merchOrderId == null              -> log + 200  (сессия не наша, ретрай не поможет)
2. select * from merch_orders where id = merchOrderId
   - ошибка чтения                   -> 500  (Stripe переотправит)
   - строки нет                      -> log + 200  (чинить нечего)
   - order.user_id !== payment.userId-> log ошибки + 200  (подделка metadata, печатать нельзя)
   - order.retail_cents !== payment.amountCents -> log + 200 (сумма разошлась, разбирается человек)
3. если status in ('draft_created','cancelled') -> 200  (повторная доставка, всё уже сделано)
4. если status === 'pending_payment':
   update merch_orders set status='paid', paid_at=..., ship_* = ... where id=? and status='pending_payment'
   - ошибка записи                   -> 500
5. если status === 'failed' и attempts >= MAX -> 200 (руками)
6. адреса нет или он неполный        -> status='failed', last_error='no shipping address' + 200
7. POST /orders?confirm=false с external_id = order.id
   - 2xx                             -> update status='draft_created', printful_order_id=... -> 200
   - 4xx «order already exists»      -> считаем успехом, см. §6.4 -> 200
   - прочие 4xx (кривые данные)      -> attempts+1, last_error, status='failed' -> 200
   - 5xx / таймаут / сеть            -> attempts+1, last_error, статус остаётся 'paid' -> 500
   - attempts достигли MAX_PRINTFUL_ATTEMPTS (5) -> status='failed' -> 200
```

Ключевое различие в последних строках. **4xx это «мы прислали ерунду», ретрай её не исправит**, поэтому `failed` и 200. **5xx и таймаут это «у них не работает»**, поэтому 500: Stripe будет переотправлять событие около трёх суток с нарастающим интервалом, и за это время Printful почти наверняка встанет. Тот же довод, что уже записан в комментарии про чужую подписку (`route.ts:222-225`): ответить 200 значит потерять событие навсегда.

Потолок попыток нужен, чтобы патологический заказ не долбил Printful трое суток. Пять попыток по нарастающему интервалу это примерно сутки, дальше разбирается человек.

### 6.3 Проверка адреса

Обязательные поля для Printful: `address1`, `city`, `country_code`, `zip`, плюс `state_code` для US/CA/AU. Плюс `name` и `email` в получателе. Проверка чистой функцией в `lib/merch/recipient.ts`:

```ts
export function recipientFrom(session: MerchSessionData): Recipient | null
```

`null` означает шаг 6 выше: `failed` с внятным `last_error`, потому что без адреса печатать физически некуда, а ретраить нечего (адрес в событии больше не появится).

### 6.4 Идемпотентность

Три независимых рубежа, и это не избыточность, а разные сценарии:

1. **`stripe_session_id unique`** в таблице. Сессия одна, заказ один.
2. **Условный `update ... where status = 'pending_payment'`** на переводе в `paid`. Повторная доставка события не перезапишет уже продвинутый статус и не сдвинет `paid_at`.
3. **`external_id` в Printful, равный нашему `order.id`.** Это тот самый рубеж, который спасает при «мы создали заказ, но не успели записать ответ»: сервер упал между шагом 7 и записью статуса, Stripe переотправил событие, мы снова шлём `POST /orders` с тем же `external_id`, Printful отвечает 4xx «order with this external_id already exists». Этот конкретный ответ обязан трактоваться как успех: заказ есть, дублей нет. Распознавать по подстроке `external_id` в тексте ошибки Printful (их API не даёт машинного кода на этот случай).

Это ровно тот же принцип, что в ledger кадров: там уникальный `(kind, ref)` в `wallet_transactions` и `p_ref = sessionId` в `ai_credits_grant` (`route.ts:113-120`). Разница только в том, что у мерча есть внешняя система, и ей нужен собственный ключ.

## 7. «Мои заказы»

Новая страница `app/account/orders/page.tsx`, серверный компонент, рядом с `app/account/billing`. Пункт в навигации аккаунта появляется всегда, даже при нуле заказов: человек, который ищет «а где мой заказ», должен найти раздел, а не вспоминать, был ли он.

Читает `readMerchOrdersAction()` из `app/actions/merch.ts`: `select` под пользовательской сессией (RLS сама отдаст только свои), `where status <> 'pending_payment'`, `order by created_at desc`, лимит 50.

Карточка заказа показывает:

- миниатюру print-файла (он публичный, ссылка уже есть),
- название товара и размер по-русски,
- дату и сумму,
- статус словами, не кодом,
- **что будет дальше** - самое важное поле и единственная причина, по которой страница вообще существует.

Тексты «что дальше» по статусам:

| Статус | Текст |
|---|---|
| `paid` | «Оплата прошла. Передаём заказ в печать, обычно это занимает несколько минут.» |
| `draft_created` | «Заказ у типографии. Печать и отправка занимают 3-7 рабочих дней. Письмо с трек-номером придёт на {email} от Printful, нашего партнёра по печати.» |
| `failed` | «Оплата прошла, но с заказом возникла заминка. Мы уже видим это и свяжемся с вами. Если хотите ускорить, напишите на {support}.» |
| `cancelled` | «Заказ отменён, деньги возвращены на карту. Возврат идёт до 10 рабочих дней, это срок банка.» |

Про Printful сказано прямым текстом ровно в одном месте: там, где иначе человек получит письмо от незнакомого отправителя и решит, что это спам. Это не раскрытие «кухни», это предотвращение обращения в поддержку.

Ссылки на трекинг в v1 нет: чтобы её показать, нужен вебхук от Printful (§11).

## 8. Ошибки и что с ними делает владелец

### 8.1 Оплата прошла, Printful упал

Разобрано в §6.2. Итог для человека: `status = 'failed'`, деньги у нас, товара нет. Это худший из возможных исходов, и он обязан быть видимым.

**Телеграм-алерта в v1 не делаем.** Заводить хук, хранить токен бота и писать доставку уведомлений ради события, которое случится ноль раз в первый месяц, дороже, чем один SQL-запрос раз в день. Вместо этого:

1. Строка `failed` с непустым `last_error` в таблице.
2. Раздел в `docs/runbook` (или прямо здесь, §8.3) с готовым запросом.
3. Красный счётчик проблемных заказов на существующей админской странице, если она есть; если нет, то без неё.

Как только заказов станет больше десятка в неделю, алерт добавляется одной строкой в вебхуке. Это осознанно отложенное, а не забытое.

### 8.2 Возврат денег

Вручную, через Dashboard Stripe. Refund на сессию, затем `update merch_orders set status = 'cancelled' where id = ...`. Автоматизировать нечего: за первые месяцы таких случаев будут единицы, и каждый стоит того, чтобы на него посмотрел человек.

### 8.3 Запрос владельца

```sql
-- Что требует внимания прямо сейчас
select id, created_at, product, size, retail_cents, status, printful_attempts, last_error, ship_country
from public.merch_orders
where status in ('paid', 'failed')
  and created_at < now() - interval '15 minutes'
order by created_at desc;
```

`paid` старше пятнадцати минут это уже аномалия: нормальный путь `paid -> draft_created` занимает секунды внутри одного вызова вебхука. Строка, застрявшая в `paid`, означает, что Stripe ещё ретраит или уже перестал.

```sql
-- Деньги за период
select date_trunc('day', paid_at) as day,
       count(*) as orders,
       sum(retail_cents) / 100.0 as revenue_usd,
       sum(cost_cents + ship_cents) / 100.0 as cost_usd,
       sum(retail_cents - cost_cents - ship_cents) / 100.0 as margin_usd
from public.merch_orders
where status = 'draft_created'
group by 1 order by 1 desc;
```

### 9.2 Что появляется

Кнопка «Купить» на каждой карточке товара в галерее (`:207-243`). Ключевое решение: **кнопка видна всегда, до и без сборки мокапов**.

Довод. Покупка не зависит от Printful-мокапа ни технически, ни по смыслу: print-файл рисуется отдельно и в другом разрешении (§3), а локальный силуэт с наложенным узором уже показывает человеку, что он получит. Прятать кнопку до мокапов значит поставить платную функцию за Pro-гейт мокапов (`useAiGate(null, 'merchMockups')`, `:71`) и потерять всех, кто не Pro. Это тот же дефект, от которого лечит вся спека: продажа не должна зависеть от расходной функции.

Карточка после доработки:

```
┌───────────────────────────┐
│ [мокап или силуэт]        │
│ Футболка                  │
│ $21.99 · доставка включена│
│ [ Купить ]                │
│ Доставка: США, ЕС, ... ⓘ  │
└───────────────────────────┘
```

Цена берётся из того же снимка каталога, что и на сервере, через общий модуль `lib/merch/pricing.ts`. Числа на клиенте и на сервере обязаны считаться одной функцией: две реализации одной формулы это гарантированное расхождение цены на карточке и в чеке. `MERCH_MARGIN` при этом серверная переменная, поэтому клиент получает **уже посчитанные цены** пропсом с сервера, а не пересчитывает их сам. Формула общая, вход разный.

### 9.3 Модалка размера

Только для футболки. Для остальных товаров клик по «Купить» ведёт сразу в Checkout.

Содержимое: четыре кнопки-чипа S/M/L/XL по образцу уже существующих чипов выбора товара (`:150-169`), таблица соответствия в сантиметрах ссылкой (Printful даёт размерную сетку, её можно просто перепечатать текстом), цена, и кнопка «Перейти к оплате».

Состояние занятости: та же механика, что у `busy` в существующем компоненте. Пока server action готовит print-файл и создаёт сессию, кнопка показывает «Готовим заказ». Это займёт 1-3 секунды (рендер 4000 px в sharp плюс заливка в Storage плюс запрос в Stripe), молчать столько нельзя.

Переход: `window.location.href = result.url`, как в остальных местах проекта. Не `router.push` - это внешний домен Stripe.

### 9.5 Гейт по конфигурации

Если `MERCH_ENABLED` выключен или нет ключей Stripe/Printful, кнопки «Купить» нет вовсе. Не заблокированной, не молчаливой - её нет. Ровно тот же вывод, что был сделан для мокапов в промо-спеке (§1.2 там): кнопка, которая ничего не делает, хуже отсутствующей кнопки.

## 11. Чего в v1 нет

Список закрытый. Всё, что здесь, реализовывать нельзя, даже если «там пять строк».

| Не делаем | Почему |
|---|---|
| Автоматические возвраты | единицы случаев, каждый достоин человека (§8.2) |
| Мультивалютность | вся касса проекта в USD, `parseOneTimeEvent` отбивает прочее |
| Stripe Tax | требует налоговой регистрации владельца в юрисдикциях; включается галочкой позже, когда будет что декларировать |
| Живой трекинг в UI | нужен вебхук от Printful (`package_shipped`), это отдельный эндпойнт с отдельной подписью; в v1 трек приходит письмом от Printful |
| Вебхуки Printful вообще | см. выше |
| Корзина и заказ нескольких товаров | одна кнопка это одна сессия; корзина потребует `merch_order_items` и пересчёт доставки |
| Количество больше одного | `quantity: 1` жёстко; доставка вшита в цену за единицу, две единицы сломали бы расчёт |
| Sync products в Printful | наши товары живут в нашем каталоге, синхронизация не нужна вовсе |
| Выбор цвета футболки | новый ряд variant_id и новые мокапы на каждый цвет |
| 2XL и больше | другая себестоимость, ломает «одну цену на все размеры» (§2.3) |
| Печать на нескольких местах (спина, рукав) | одна область печати на товар |
| Живой расчёт доставки | обоснование в §2.4 |
| Промокоды | скидка на товар с фиксированной себестоимостью уводит в минус |
| Покупка без аккаунта | некому показать статус (§4.1) |
| Телеграм-алерт при `failed` | преждевременно (§8.1) |

### 13.2 E2E с моками

Playwright, спека `e2e/merch.spec.ts`. Printful и Stripe замоканы на уровне маршрутов:

1. Кнопка «Купить» видна на всех четырёх карточках при `MERCH_ENABLED=true` и не видна при выключенном.

4. Клик по «Перейти к оплате» уводит на замоканный `checkout.stripe.com`.
5. Аноним видит приглашение войти, а не редирект в никуда.

### 13.3 Живая проверка руками

Порядок обязательный, отступать нельзя:

1. **Stripe в test mode.** Карта `4242 4242 4242 4242`, любая будущая дата, любой CVC. Адрес доставки американский, с обязательным штатом.
2. После оплаты убедиться, что в `merch_orders` статус `draft_created` и заполнен `printful_order_id`.
3. **Открыть кабинет Printful, найти черновик.** Проверить глазами: тот ли товар, тот ли размер, тот ли узор, не съехал ли макет, цена в `retail_costs` совпадает с оплаченной.
4. **Черновик не подтверждать.** `confirm=false` существует ровно для этого: баланс не тратится, футболка не печатается. Удалить черновик после проверки.
5. Повторить для кружки (другая область печати, `placement = default`) и постера (самый большой файл, проверка потолка 4000 px).
6. Проверить европейский адрес без штата: заказ обязан пройти, `state_code` не должен уехать пустой строкой.
7. **Проверить повтор события.** В Dashboard Stripe нажать «Resend» на `checkout.session.completed`. В Printful не должно появиться второго черновика, статус в базе не должен измениться.
8. Проверить отказ: временно испортить `PRINTFUL_API_KEY`, оплатить, убедиться, что заказ ушёл в `failed` с внятным `last_error`, а деньги видны в Stripe и подлежат возврату.

Пункт 7 самый важный. Дублирующийся заказ у печатника это реальные деньги на реальном балансе, и проверить защиту от него надо до первого живого покупателя, а не после.
