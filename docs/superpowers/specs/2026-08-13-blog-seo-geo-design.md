# Блог, SEO и GEO: раздел статей на endgrain.app и разметка под людей и ИИ

Дата: 13 августа 2026. Статус: принят к реализации. Закрывает пункты 7 и 8 из `docs/tech-debt.md`.
Этот документ - единственный источник требований по кластеру. Всё, чего в нём нет, делать не надо.

## 0. Что мы вообще решаем

Три задачи, связанные одной причиной. Блог нужен не сам по себе, а потому что без собственных страниц с текстом оптимизировать нечего: лендинг и тарифы это две страницы, их не хватит ни поисковику, ни ИИ-ассистенту, чтобы понять, что мы вообще за продукт. SEO нужен, чтобы эти страницы правильно читались роботами Google. GEO нужен, чтобы их цитировали ChatGPT, Perplexity и Gemini, а это другой набор требований: там важна не плотность ключевых слов, а то, насколько легко из страницы вырезать готовый абзац-ответ.

Ограничение по ресурсу простое: до сдачи конкурса. Поэтому всё, что можно сделать файлами в репозитории и чистыми функциями с юнит-тестами, делается так. Ничего, что требует админки, редактора в браузере или новой таблицы в Supabase, в этот кластер не входит.

## 1. Хранение статей: MDX в репозитории

### Решение

Статьи лежат в `content/blog/*.mdx`. База данных не используется.

### Обоснование

Сравнивали честно, вот таблица.

| | MDX в репозитории | Записи в Supabase |
|---|---|---|
| Время до первой статьи | час: положил файл, задеплоил | день-два: таблица, RLS, админка, редактор |
| Кто пишет | автор через Claude Code, то есть уже настроенный процесс | нужен интерфейс, иначе правки идут SQL-ом |
| Рендер | статика на билде, ноль запросов в рантайме | запрос в БД на каждый рендер или ISR с ревалидацией |
| Ревью и откат | git diff, git revert, PR | никак, только руками в таблице |
| Картинки | `public/blog/<slug>/`, тот же деплой | Storage, отдельный bucket, отдельные правила доступа |
| Цена ошибки | сборка падает на билде, до прода не доедет | текст с битым markdown прилетает в прод живьём |
| Публикация без деплоя | нет | да |
| Много авторов | плохо | хорошо |

Два минуса MDX реальны: нельзя опубликовать статью без деплоя и неудобно нескольким авторам. Оба к нам не относятся. Автор один, деплой на Vercel занимает пару минут и запускается пушем в main, что и так происходит при любой правке. Взамен мы получаем то, что для конкурсного продукта важнее всего: статьи проверяются на билде, участвуют в типизации и не могут отвалиться в проде из-за недоступной базы.

Отдельно: база пригодилась бы, если бы статьи писали пользователи или их нужно было бы редактировать из веб-интерфейса. Ни того ни другого в продукте нет и в рамках конкурса не будет. Переезжать с MDX на БД, если такое понадобится, дёшево: слой доступа к статьям спрятан за четырьмя функциями в `lib/blog/posts.ts`, страницы про хранилище не знают.

### Как это устроено технически, с учётом Next 16

Гайд `node_modules/next/dist/docs/01-app/02-guides/mdx.md` прочитан. Существенное для нас:

**`useMDXComponents()` в Next 16 не принимает аргументов.** Это ломающее изменение относительно Next 15, где функция получала пришедшие компоненты и должна была их смёржить. Файл `mdx-components.tsx` в корне проекта обязателен, без него `@next/mdx` в App Router просто не работает.

**`pageExtensions` мы не трогаем.** Дефолтный способ из гайда - положить `page.mdx` в `app/` и добавить `md`/`mdx` в `pageExtensions`. Нам это не подходит: маршрут статьи должен быть один динамический сегмент с общей обвязкой (шапка, хлебные крошки, JSON-LD, OG), а не тридцать одинаковых папок. Поэтому используем второй описанный в гайде способ: динамический импорт по slug из `app/(landing)/blog/[slug]/page.tsx`, `generateStaticParams` из реестра, `dynamicParams = false`. Побочная выгода: `pageExtensions` остаётся дефолтным, и ни один `.md` в репозитории случайно не станет страницей.

**Frontmatter `@next/mdx` не поддерживает.** Гайд предлагает три плагина или `gray-matter`. Мы не берём ни один: MDX умеет обычные ES-экспорты, и мы объявляем метаданные прямо в файле как `export const meta`. Это дешевле (минус зависимость), типизируется и валидируется зодом, который в проекте уже есть.

```mdx
// content/blog/kerf-i-pripuski.mdx
export const meta = {
  slug: 'kerf-i-pripuski',
  lang: 'ru',
  title: 'Пропил и припуски: почему доска выходит уже, чем в чертеже',
  description: 'Каждый рез съедает 3 мм. На доске из 24 полос это 69 мм потери. Как заложить их в расчёт заранее.',
  answer: 'Ширина заготовки под первую склейку равна сумме полос плюс произведение числа резов на толщину пропила плюс припуск на выравнивание кромок, обычно 6 мм на всю панель.',
  date: '2026-08-14',
  updated: '2026-08-14',
  tags: ['раскрой', 'расчёт'],
  cover: '/blog/kerf-i-pripuski/cover.jpg',
  readingMinutes: 6,
}

## Сколько съедает один пропил
...
```

**Плагины remark и rehype в Turbopack задаются строками.** Next 16 собирает Turbopack-ом по умолчанию, а через границу JS/Rust функцию передать нельзя. Отсюда прямое следствие, которое надо помнить при реализации: `rehype-autolink-headings` мы поставить **не можем**, его настройка требует функции в опции `content`. Берём только то, что сериализуемо:

```ts
// next.config.ts
import createMDX from '@next/mdx'

const withMDX = createMDX({
  options: {
    remarkPlugins: ['remark-gfm'],
    rehypePlugins: ['rehype-slug'],
  },
})

export default withMDX(nextConfig)
```

`remark-gfm` нужен ради таблиц: половина полезного текста про раскрой это таблица размеров. `rehype-slug` проставляет `id` заголовкам, а якорь-ссылку рисуем сами в маппинге `h2` внутри `mdx-components.tsx`. Якоря обязательны и для людей, и для GEO: ИИ-ассистенты цитируют ссылкой на конкретный раздел.

**Плагин типографики Tailwind не ставим.** `@tailwindcss/typography` принёс бы свою палитру, которая начала бы спорить с токенами проекта (`bg-canvas`, `text-ink`, `text-ink-secondary`). Вместо него в `mdx-components.tsx` явный маппинг тегов на классы проекта: `h2`, `h3`, `p`, `ul`, `ol`, `li`, `a`, `blockquote`, `code`, `pre`, `table`, `th`, `td`, `img`, `hr`. Пятнадцать строк, зато дизайн-система одна.

Картинка мапится на `next/image` (как в примере из гайда), файлы лежат в `public/blog/<slug>/`. Обложка статьи это `meta.cover`, она же уходит в OG и в JSON-LD.

### Реестр статей

Итерировать директорию через `fs` на сервере можно, но это ломает статическую сборку и не типизируется. Вместо этого явный реестр:

```ts
// lib/blog/registry.ts
import { meta as kerf } from '@/content/blog/kerf-i-pripuski.mdx'
import { meta as species } from '@/content/blog/vybor-porod.mdx'

export const POST_METAS = [kerf, species] as const
```

Тело статьи грузится динамически по slug (`await import(\`@/content/${slug}.mdx\`)`), в реестре только метаданные. Минус один: новую статью надо дописать в реестр руками. Закрываем его тестом: `lib/blog/registry.test.ts` читает директорию `content/blog` через `fs` (в тесте это можно) и падает, если файл есть, а в реестре его нет. Забыть физически не получится.

Поверх реестра `lib/blog/posts.ts`:

- `allPosts()` - валидирует каждый `meta` зод-схемой, сортирует по дате убыванием, отбрасывает записи с `draft: true`;
- `postBySlug(slug)`;
- `postsByTag(tag)`;
- `allTags()` - уникальные теги со счётчиками, отсортированы по частоте.

Всё чистое, всё под vitest. Валидация зодом здесь не украшение: опечатка в дате или отсутствующий `description` иначе доедут до sitemap и до JSON-LD, где превратятся в невалидную разметку.

## 2. Двуязычность блога

В проекте язык живёт в cookie `eg-locale`, а не в URL. Для лендинга это работает, для блога так делать нельзя: один URL, отдающий разный текст в зависимости от куки, поисковик индексирует как попало, а для ИИ-краулера, который куку не ставит, это просто русская страница с английским заголовком.

Решение: **язык это свойство статьи, а не читателя.** Каждая статья одноязычна, поле `meta.lang` обязательно. Обвязка страницы (шапка, кнопки, подписи «читать далее», названия тегов интерфейса) следует общей куке, как везде в проекте. Текст статьи не меняется никогда.

Следствия:

- на `<article>` ставится `lang={meta.lang}` явно, потому что `<html lang>` в корневом layout определяется кукой и может не совпадать;
- в метаданных статьи `openGraph.locale` берётся из `meta.lang`, в JSON-LD это `inLanguage`;
- лента `/blog` показывает все статьи, у карточки на «чужом» языке стоит бейдж языка;
- если у статьи есть перевод, в `meta.translationOf` указывается slug пары, и на обеих страницах проставляется `alternates.languages`. Пока пар нет - поле не заполняется, механика лежит готовой.

Один URL - один язык - один канон. Никаких `?lang=`, никаких вариаций по куке в индексируемом контенте.

## 3. Роутинг: как /blog попадает на нужный домен

Сейчас `proxy.ts` для роли `site` пропускает ровно два пути (`/` и `/landing`), а всё остальное редиректит 307 на `app.endgrain.app`. Блог живёт на домене лендинга, значит правило надо расширить, и расширять его надо не приписыванием `if` в прокси, а списком в `lib/routing/host.ts` - там единственное место, где вообще записано, что куда относится.

```ts
// lib/routing/host.ts
/** Пути, которые обслуживает домен лендинга. Всё остальное на нём уезжает в студию. */
const SITE_PREFIXES: readonly string[] = ['/blog']

export function isSitePath(pathname: string): boolean {
  if (pathname === '/' || pathname === LANDING_PATH) return true
  return SITE_PREFIXES.some((p) => pathname === p || pathname.startsWith(`${p}/`))
}
```

В `proxy.ts` ветка `site` становится такой: `/` переписывается на `/landing`, всё, для чего `isSitePath` истинно, пропускается через `NextResponse.next()`, остальное редиректится на app-домен как раньше.

Симметрично, ветка `app` уже редиректит `/landing` на корневой домен 308-м, чтобы не плодить дубли. Ровно то же самое нужно для блога: `app.endgrain.app/blog/что-угодно` отдаёт 308 на `endgrain.app/blog/что-угодно`. Иначе у каждой статьи появляется вторая копия по второму домену, а это ровно та проблема, ради которой в прокси уже написан комментарий про канон.

Роль `unknown` (localhost, 127.0.0.1, превью на vercel.app) ведёт себя как раньше: домены не разводятся, `/blog` открывается напрямую. Именно на этом работают e2e.

И ещё одно, без чего блог на превью и локально просто не откроется: в `lib/auth/access.ts` в `PUBLIC_PREFIXES` надо добавить `/blog`, а в `PUBLIC_FILES` - `/llms.txt`. Забыть про это легко, а симптом будет странный: локально блог редиректит на `/login`.

## 4. llms.txt на обоих доменах

Отдаём route handler-ом: `app/llms.txt/route.ts` с `export const dynamic = 'force-static'`. Папка с точкой в имени - это рабочая конвенция App Router, файл отдаётся как `/llms.txt` с `Content-Type: text/plain; charset=utf-8`.

Почему это автоматически решает требование «на обоих доменах»: матчер прокси исключает пути, оканчивающиеся на `.txt` и `.xml`. То есть `/llms.txt` (как и `/robots.txt`, и `/sitemap.xml`) до прокси вообще не доходит, редирект на app-домен к нему не применяется, и он одинаково открывается и на `endgrain.app`, и на `app.endgrain.app`. Ничего специально настраивать не нужно, но проверить это на проде обязательно - это как раз тот случай, где «должно работать» и «работает» расходятся.

Содержимое собирается чистой функцией `lib/geo/llms.ts` из того же реестра статей, что и sitemap. Формат по спеке llmstxt.org, зафиксированной в `docs/research/agent-ready-saas.md`: H1, блоквот-описание одной строкой, свободный текст, дальше секции `##` со ссылками вида `- [Название](URL): описание`.

```
# Endgrain Studio

> Производственный инструмент для торцевых разделочных досок: узор, схема распила и переклеек, размеры деталей, расчёт материала и себестоимости, печатная инструкция в PDF.

Все размеры в миллиметрах, дюймы только представление. Расчёты учитывают толщину пропила (kerf) и припуски на выравнивание.

## Продукт

- [Endgrain Studio](https://endgrain.app/): что делает инструмент и для кого
- [Студия](https://app.endgrain.app/): редактор узора, расчёты и экспорт
- [Тарифы](https://app.endgrain.app/pricing): Free и Pro, что входит в каждый

## Блог

- [Пропил и припуски](https://endgrain.app/blog/kerf-i-pripuski): каждый рез съедает 3 мм, как заложить это в расчёт

## Optional

- [RSS](https://endgrain.app/blog/rss.xml): лента статей
- [Карта сайта](https://endgrain.app/sitemap.xml)
```

Описание каждой статьи в llms.txt - это `meta.answer`, обрезанный до одного предложения, а не `meta.description`. Разница принципиальная: `description` написан для человека в выдаче, `answer` написан как готовый факт для цитирования.

`llms-full.txt` (полные тексты статей одним файлом) в этот кластер не входит. Он имеет смысл при двух десятках статей, а не при трёх.

## 5. Schema.org

Разметка только JSON-LD, микроформатов не пишем. Генерация - чистые функции в `lib/seo/jsonld.ts`, вставка - серверный компонент `components/seo/JsonLd.tsx`, который рендерит `<script type="application/ld+json">`. Функции возвращают простые объекты, тесты проверяют обязательные поля и то, что все URL абсолютные.

Что и где:

**Лендинг (`/`, он же `/landing`)** отдаёт `@graph` из трёх узлов, связанных через `@id`:

- `Organization` - `name`, `url`, `logo` (абсолютный URL на `/icon.svg` или PNG), `description`, `sameAs` (профили; пока пусто, поле не выводим вовсе, а не выводим пустым массивом);
- `WebSite` - `name`, `url`, `inLanguage`, `publisher` ссылкой на `@id` организации;
- `SoftwareApplication` - `name`, `applicationCategory: 'DesignApplication'`, `operatingSystem: 'Web'`, `url` на app-домен, `offers` двумя `Offer` (0 USD и 7 USD/месяц), `featureList` списком из того, что реально умеет продукт.

`SoftwareApplication` дублируется на `/pricing`, потому что именно там цены, и именно оттуда Google берёт их для карточки. `aggregateRating` не выводим: отзывов нет, а выдуманный рейтинг это разметка, за которую санкционируют.

**Лента `/blog`** - `Blog` с `blogPost` списком (`BlogPosting` в сокращённом виде: `headline`, `url`, `datePublished`).

**Статья `/blog/<slug>`** - `@graph` из `BlogPosting` и `BreadcrumbList`. В `BlogPosting`: `headline` (до 110 символов, длиннее Google обрезает), `description`, `image` абсолютным URL обложки, `datePublished`, `dateModified` (из `meta.updated`, а не из даты сборки - иначе каждый деплой врёт, что все статьи обновились), `author` типом `Person`, `publisher` ссылкой на `@id` организации, `inLanguage` из `meta.lang`, `mainEntityOfPage`, `keywords` из тегов.

Хлебные крошки: Endgrain Studio -> Блог -> Заголовок. Они же рисуются на странице визуально, а не только в разметке.

## 6. Канонические URL и Open Graph

Корневой layout сейчас ставит `metadataBase: APP_ORIGIN`. Для страниц лендингового домена это неверно, и лендинг уже обходит это, переопределяя `metadataBase` у себя. Плодить такое переопределение по каждой странице не надо: заводим `lib/seo/metadata.ts` с двумя хелперами - `siteUrl(path)` и `appUrl(path)`, собирающими абсолютный адрес от нужного origin, и `pageMetadata({...})`, который из заголовка, описания, канона и типа собирает готовый объект `Metadata` вместе с `openGraph` и `twitter`. Все публичные страницы вызывают его, а не пишут OG руками.

Каноны:

| Страница | Канон |
|---|---|
| `/` и `/landing` на любом домене | `https://endgrain.app/` |
| `/blog` | `https://endgrain.app/blog` |
| `/blog/<slug>` | `https://endgrain.app/blog/<slug>` |
| `/blog/tag/<tag>` | `https://endgrain.app/blog/tag/<tag>` |
| `/pricing` | `https://app.endgrain.app/pricing` |
| студия `/` | `https://app.endgrain.app/` |

Лендинг сейчас указывает каноном `SITE_ORIGIN` без слеша. Приводим к виду со слешем и следим, чтобы канон, sitemap и llms.txt писали адрес одинаково: `https://endgrain.app/`. Расхождение в один слеш между тремя источниками - классическая причина, по которой Google выбирает канон сам и не тот.

Страницы тегов при этом ставим `robots: { index: false, follow: true }`. Они полезны читателю, но это перетасовка тех же статей, и в индексе им делать нечего.

Open Graph:

- лендинг - уже есть динамическая `opengraph-image.tsx`, оставляем как есть;
- статья - своя `app/(landing)/blog/[slug]/opengraph-image.tsx`, тот же визуальный шаблон (фон `#EFEAE1`, полосы четырёх пород справа, шрифт PT Sans из `public/fonts`), но текст - заголовок статьи, а сверху надпись «Блог · Endgrain Studio». Заголовок берётся из реестра по slug, размер шрифта подбирается по длине (84 px до 40 символов, дальше 64 px), иначе длинные заголовки выезжают за карточку;
- лента блога и `/pricing` - без собственных картинок, используют картинку лендинга через `metadataBase`;
- `twitter: { card: 'summary_large_image' }` везде, где есть картинка.

## 7. RSS

`app/(landing)/blog/rss.xml/route.ts`, `dynamic = 'force-static'`, `Content-Type: application/rss+xml; charset=utf-8`. Библиотеку не ставим: RSS 2.0 для десяти полей это сорок строк сериализатора в `lib/blog/rss.ts`, зато он чистый и покрывается тестом на экранирование (амперсанд и угловые скобки в заголовке ломают фид молча, и заметить это без теста невозможно).

В канале: `title`, `link`, `description`, `language`, `lastBuildDate`. В `item`: `title`, `link`, `guid` с `isPermaLink="true"`, `pubDate` в RFC 822, `description` из `meta.description` в CDATA. Полные тексты в фид не кладём.

`<link rel="alternate" type="application/rss+xml">` добавляется в `metadata.alternates.types` на `/blog` и на каждой статье.

Замечание про домены: путь оканчивается на `.xml`, значит матчер прокси его пропускает, и фид открывается и с app-домена тоже. Ссылки внутри фида абсолютные и ведут на канон, так что вреда нет, но в `robots.txt` app-домена смысла его светить не будем - в sitemap попадает только каноничный адрес.

## 8. Sitemap и robots

`app/sitemap.ts` расширяется до реестра статей:

```ts
export default function sitemap(): MetadataRoute.Sitemap {
  const posts = allPosts()
  return [
    { url: `${SITE_ORIGIN}/`, priority: 1.0, changeFrequency: 'weekly' },
    { url: `${SITE_ORIGIN}/blog`, priority: 0.7, changeFrequency: 'weekly',
      lastModified: posts[0]?.updated ?? posts[0]?.date },
    ...posts.map((p) => ({
      url: `${SITE_ORIGIN}/blog/${p.slug}`,
      lastModified: p.updated ?? p.date,
      priority: 0.6,
      changeFrequency: 'yearly' as const,
    })),
    { url: `${APP_ORIGIN}/`, priority: 0.8 },
    { url: `${APP_ORIGIN}/pricing`, priority: 0.6 },
  ]
}
```

Страницы тегов в sitemap не идут: они `noindex`. `lastModified` берётся из метаданных статьи, а не из `new Date()`.

`app/robots.ts` правится в двух местах. Первое: в `disallow` добавляется `/api/` - сейчас его там нет, и вебхук Stripe формально открыт для обхода. Второе: комментарий про «отдаётся с обоих доменов одинаково» остаётся верным и после наших правок, потому что sitemap ссылается абсолютным адресом на канон.

ИИ-краулеров (`GPTBot`, `ClaudeBot`, `PerplexityBot`, `Google-Extended`, `OAI-SearchBot`) **не блокируем и отдельных правил под них не пишем**. Общее `allow: /` их и так пропускает, а лишние секции в robots.txt это лишний способ ошибиться. Цель кластера - чтобы нас цитировали, а не чтобы не пускали.

## 9. GEO: как писать страницы, чтобы их цитировали

Это не про разметку, а про структуру текста, и это половина ценности пункта 8. Правила обязательны для каждой статьи и проверяются глазами при ревью.

**Блок ответа сверху.** Первое, что идёт после H1, - компонент `<Answer>` из `components/blog/Answer.tsx`: два-три предложения, которые полностью отвечают на вопрос из заголовка, без «в этой статье мы разберём». Текст блока дублируется в `meta.answer` и оттуда попадает в llms.txt. Именно этот абзац ИИ вырежет и процитирует, всё остальное он использует как подтверждение.

**Заголовки формулируются вопросами.** Не «Толщина пропила», а «Сколько миллиметров съедает один пропил». Ассистенты матчат запрос пользователя на текст заголовка, и вопросительная формулировка попадает точнее.

**Числа с единицами и условиями.** Не «пропил около трёх миллиметров», а «3 мм для полотна 40 зубьев на 250-мм диске». Утверждение без условий нечитаемо как факт и не цитируется.

**Таблицы вместо перечислений там, где данные табличные.** Размеры, породы, расход. Таблица извлекается моделью надёжнее прозы, и это как раз то, ради чего в конфиг добавлен `remark-gfm`.

**Даты и авторство видимы.** Дата публикации и дата обновления печатаются на странице, а не только в JSON-LD. Свежесть - один из немногих сигналов, по которым ассистент выбирает между двумя одинаково релевантными источниками.

**Внутренняя перелинковка.** Каждая статья ссылается на студию как минимум один раз в контексте («посчитать это можно в редакторе»), и минимум на одну соседнюю статью. Лендинг получает ссылку на блог в подвале (`components/landing/LandingFooter.tsx`), лента блога - ссылку на студию и на тарифы.

Отдельно про лендинг: секции лендинга получают `id` и осмысленные H2 (часть уже есть: `#patterns`), чтобы на них можно было сослаться якорем. Это дешёвая правка с прямым эффектом на цитируемость.

## 12. Проверка

Юнит-тестами закрываются `posts`, `registry`, `rss`, `jsonld`, `metadata`, `llms`, плюс дополненные `host` и `access`. Это чистые функции, моков не требуется.

E2E (`e2e/blog.spec.ts`, `e2e/seo.spec.ts`) на `127.0.0.1`, где роль хоста `unknown` и домены не разводятся:

1. `/blog` открывается без логина, показывает три карточки, у каждой заголовок и дата;
2. переход по карточке ведёт на статью, в ней есть H1, блок-ответ, хлебные крошки, дата обновления;
3. на статье ровно один `script[type="application/ld+json"]`, он парсится, в нём `BlogPosting` с непустыми `headline`, `datePublished`, `image`;
4. `link[rel=canonical]` на статье совпадает с ожидаемым каноном;
5. `/blog/tag/раскрой` отдаёт подмножество и содержит `noindex`;
6. `/blog/rss.xml` парсится как XML и содержит три `item`;
7. `/llms.txt` отдаётся как `text/plain`, начинается с `# Endgrain Studio`, вторая непустая строка начинается с `>`;
8. `/sitemap.xml` содержит URL всех трёх статей;
9. несуществующий slug отдаёт 404 (следствие `dynamicParams = false`).

Ручная проверка на проде после деплоя, без неё задача не закрыта:

- `endgrain.app/blog` открывается, `app.endgrain.app/blog` отдаёт 308 на корневой домен;
- `/llms.txt` открывается на обоих доменах;
- валидатор Rich Results Google не ругается на лендинг и на статью;
- карточка статьи в отладчике OG показывает нужную картинку и заголовок.
