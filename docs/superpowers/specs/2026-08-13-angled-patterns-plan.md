## 0. Ключевые решения, которые уточняют спеку

Спека писалась как оценка, а не как чертёж. При разборе кода вскрылись пять мест, где план
отличается от неё. Отличия сознательные, каждое сокращает объём и риск.

### 0.1 Cell = bbox плюс необязательный полигон

Спека предлагала заменить прямоугольник полигоном. Замена ломает разом 12 потребителей
`model.cells` и убивает возможность параллелить фазу 2.

Вместо этого `Cell` **сохраняет** `xMm`, `yMm`, `widthMm`, `heightMm` (теперь это габаритный
бокс ячейки, для прямого реза совпадает с самой ячейкой) и получает необязательное поле
`poly?: readonly Pt[]` - выпуклый многоугольник из 3-6 вершин, обход по часовой стрелке в
экранных координатах.

Правило, единое для всей фазы 2: **`poly === undefined` означает «ячейка это в точности её
bbox»**, и каждый потребитель обязан оставить существующую ветку кода дословно нетронутой
для этого случая, а новую ветку писать рядом. Это даёт три вещи сразу: побитовую регрессию
при `angleDeg = 0` не нужно доказывать, она следует из структуры кода; ни один из 164 тестовых
файлов не переписывается; потребителей фазы 2 можно раздать пятерым агентам одновременно.

Нулевая стоимость по памяти при прямом резе: поля просто нет в объекте.

### 0.2 Реализуется только `SliceRef.angleDeg`, `Row.angleDeg` остаётся заблокированным

Chevron, diamond и tumbling blocks в торцевой технике получаются из **углового реза первого
щита** (`SliceRef.angleDeg`), а не из углового реза финального щита (`Row.angleDeg`).
Цепочка: щит P1 из полос -> угловой рез P1 -> срезы вклеиваются колонками в P2 ->
**прямой** поперечный рез P2 -> ряды доски.

Пока `Row.angleDeg = 0`, доска остаётся прямоугольником. Из этого следует, что не нужны:
`render2d/layout.ts` (габарит по-прежнему ширина панели на сумму толщин рядов), приведение
собранного параллелограмма к прямоугольнику, два дополнительных треугольника отхода на
финальной склейке, пересмотр `RAGGED_BOARD`. Это минус примерно день работы и минус самый
неприятный каскад в проекте.

`Row.angleDeg != 0` продолжает отбиваться ошибкой, код диагностики переименовывается в
`ANGLE_ROW_UNSUPPORTED`, текст меняется на честный: «угловой поперечный рез финального щита
пока не поддерживается, угол задаётся на вклеенном срезе».

### 0.3 `flipRule` в документ не попадает

Спека предлагала завести в модели правило чередования. Это лишняя сущность: чередование
полностью выражается через уже имеющиеся поля отдельных `SliceRef` (знак `angleDeg` и
`offsetMm` по колонкам). Правило чередования это знание **генератора** о том, какие числа
проставить, и живёт оно в `lib/generators/angled.ts`.

В `SliceRef` добавляется ровно одно поле: `flip?: boolean` (зеркалит порядок полос внутри
среза). Документ остаётся тупым, инвариант «V не разъезжается» становится проверяемым
property-тестом над готовым `Design`, а не доверием к enum.

### 0.4 Проверки «минимальная ширина полосы по нормали к резу» не будет

Разбор геометрии (раздел 0.5) показывает: расстояние между соседними границами полос внутри
среза измеряется по нормали и равно исходной ширине полосы `w`, угол его не меняет.
Существующего `MIN_STRIP_WIDTH` достаточно. Изобретать проверку не нужно.

### 0.5 Геометрия, выведенная явно (реализаторам читать обязательно)

Это место, где ошибётся любой, кто пойдёт по интуиции. Обозначения: `φ` = `SliceRef.angleDeg`
в радианах, `c = cos φ`, `s = tan φ`, `t` = `ref.thicknessMm` (ширина колонки на доске),
`w_k` = ширина k-й полосы внутренней панели, `W` = `panelWidthMm(inner)`.

Срез, снятый с щита P1 под углом φ, это косой слой. В нём:

- **длина среза вдоль реза** равна `W / c`. Это габарит заготовки, он должен покрывать длину
  панели P2;
- **протяжённость k-й полосы вдоль длины доски** равна `w_k / c`, а не `w_k`. Соответственно
  период повторения `cycleMm` внутри колонки равен `(Σ w_k) / c`. Ровно здесь ошибаются:
  в текущем коде `cycleMm` это сумма ширин, и делить её надо;
- **граница между полосами внутри колонки наклонена**: для колонки, занимающей на доске
  `x ∈ [x0, x0 + t]`, граница идёт по прямой `y = base + (x - x0) · s`. Полный сдвиг границы
  поперёк колонки равен `t · s`, то есть амплитуда «зубца» шеврона задаётся **толщиной среза**,
  а не шириной щита. Крупный шеврон требует толстых срезов (60-100 мм), из тонких получается
  мелкая пила. Это надо помнить при подборе коридоров генератора;
- **потери на щите P1**: угловой рез входит в щит и выходит из него по треугольнику катетами
  `W` и `W · |s|`. На каждую группу резов одного угла тратится один такой треугольник длиной
  `W · |s|` вдоль оси щита и площадью `W² · |s| / 2`;
- **сцепка соседних колонок**: если колонка k имеет угол `φ_k` и ширину `t_k`, а её граница на
  правом краю оказалась на `y = base_k + t_k · s_k`, то для непрерывной линии V у колонки
  `k+1` должно быть `base_{k+1} = base_k + t_k · s_k`. Через это выражается `offsetMm`.

## 1. Инварианты, обязательные для всех фаз

Эти утверждения проверяются тестами и не подлежат обсуждению внутри шага.

1. **Регрессия нуля.** Для любого документа, где все `angleDeg = 0`, `compile()` возвращает
   результат, идентичный текущему по `JSON.stringify` (в том числе отсутствует поле `poly`),
   а любой потребитель `model.cells` идёт по прежней ветке кода.
2. **Разбиение без дыр.** Сумма площадей ячеек ряда равна площади ряда с точностью
   `GEOM_EPS_MM`.
3. **Разбиение без наложений.** Площадь пересечения любых двух ячеек равна нулю с той же
   точностью.
4. **Выпуклость и вложенность.** Каждая ячейка выпукла и лежит внутри габарита доски.
5. **Стабильность id.** Формат `${rowId}:${elementIndex}` и `${rowId}:${elementIndex}:${k}`
   не меняется, и при `φ = 0` нумерация `k` совпадает с сегодняшней. На id завязаны
   `touchedCellIds`, покраска и селекторы e2e.
6. **Честность вниз по течению.** Никакая ячейка не рисуется иначе, чем описана в схеме
   распила. Если превью показывает наклон, cutlist обязан показывать угловой рез.

Инварианты 2-4 не случайны, а следуют из конструкции: наклонные полосы образуют разбиение
всей плоскости параллельными полосами, а ячейка получается отсечением прямоугольника колонки
этим разбиением. Отсечение разбиения остаётся разбиением. Реализация обязана держаться этой
схемы, а не собирать вершины вручную.

## 2. Фаза 1. Ядро. Строго последовательно

Пять шагов, каждый следующий начинается после зелёных тестов предыдущего. Один агент на шаг,
модель `sonnet`.

### Шаг 1.1 `lib/engine/geometry.ts` (новый файл)

**Что делается.** Изолированная библиотека выпуклой геометрии, без единого импорта из движка.

```ts
export type Pt = readonly [number, number]
export function clipHalfPlane(poly: readonly Pt[], a: number, b: number, cc: number): Pt[]
export function polygonAreaMm2(poly: readonly Pt[]): number
export function polygonBbox(poly: readonly Pt[]): { xMm; yMm; widthMm; heightMm }
export function rectPoly(xMm, yMm, widthMm, heightMm): Pt[]
export function insetConvex(poly: readonly Pt[], dMm: number): Pt[]
export function polygonsOverlapMm2(a: readonly Pt[], b: readonly Pt[]): number
```

`clipHalfPlane` это Сазерленд-Ходжман по одной полуплоскости `a·x + b·y <= cc`, вершины ближе
`GEOM_EPS_MM` схлопываются. `insetConvex` реализуется через `clipHalfPlane` по каждому ребру,
сдвинутому внутрь на `dMm`: для прямоугольника даёт ровно тот же результат, что сегодняшнее
вычитание зазора, и это переиспользуется и в 2D, и в 3D, и в экспорте.
`polygonsOverlapMm2` нужен только тестам, но живёт в проде, чтобы property-тест не тащил
вторую реализацию.

**Тесты:** новый `lib/engine/geometry.test.ts` и `lib/engine/geometry.property.test.ts`
(fast-check): площадь прямоугольника; отсечение прямоугольника наклонной прямой даёт две части,
сумма площадей равна исходной; отсечение полуплоскостью, не пересекающей полигон, даёт либо
пустой список, либо исходный; выпуклость сохраняется; `insetConvex` прямоугольника на `d` даёт
прямоугольник со сторонами меньше на `2d`; `insetConvex` на слишком большое `d` даёт пустой
полигон, а не вывернутый.

**Готово когда:** `pnpm vitest lib/engine/geometry` зелёный, файл не импортирует ничего из
проекта кроме `GEOM_EPS_MM`.

### Шаг 1.3 `lib/engine/panels.ts`

**Что делается.** Вся арифметика материала под углом. Формулы:

```
sliceLengthMm(slice)   = sourceWidthMm / cos(φ)
angledWasteMm2(panel)  = Σ по различным углам g != 0:  W² · |tan φ_g| / 2
panelLengthMm(design, panelId) =
      Σ_k (t_k + planingAllowance + trim_k) / cos(φ_k)
    + Σ_{k>0} kerf / cos(φ_k)
    + Σ по различным углам g != 0:  W · |tan φ_g|
```

При всех `φ = 0` формула сворачивается в сегодняшнюю дословно (`cos 0 = 1`, `tan 0 = 0`,
второе слагаемое даёт `kerf · (n-1)`), это и есть проверка на регрессию.

Смысл третьего слагаемого: каждая группа резов одного угла требует одного захода пилы в щит,
и клин на входе уходит в отход. Группировка по различным углам, а не по числу резов: подряд
идущие резы одного угла срезаются с одной настройки салазок.

Заполняется `sourceWidthMm` в `slicesOfPanel`.

**Тесты:** правка `lib/engine/panels.test.ts` плюс новые кейсы: при `φ = 0` все числа те же,
что сегодня (тест на конкретных значениях, не на формуле); `panelLengthMm(φ) >= panelLengthMm(0)`
и монотонно растёт по `|φ|` (property, fast-check); при `φ = 45°` и одном срезе длина щита равна
`(t + allow + trim) · √2 + W` с точностью `1e-9`; `sliceLengthMm` при `φ = 60°` равен `2W`.

**Готово когда:** `pnpm vitest lib/engine/panels` зелёный и старые ожидания в файле не правились
(кроме добавления поля `sourceWidthMm` в фикстуры).

### Шаг 1.4 `lib/engine/compile.ts`

Самый содержательный шаг. Правится только `expandSliceRef`, около 100 строк.

**Что делается.**

```
c = cos(φ), s = tan(φ)
extent_k  = elementExtentMm(strip_k) / c          // было: без деления
cycleMm   = Σ extent_k                             // соответственно тоже /c
ordered   = (row.flip XOR ref.flip) ? reverse(strips) : strips
sSigned   = s, знак переворачивается при row.mirror и при (row.flip XOR ref.flip)
```

Колонка занимает `x ∈ [xMm, xMm + t]`, ряд занимает `y ∈ [rowTop, rowBottom]`.
Прямоугольник колонки `rect = rectPoly(xMm, rowTop, t, row.thicknessMm)`.
Полоса номер `k` ограничена двумя параллельными прямыми
`y - (x - xMm) · sSigned = base_k` и `... = base_k + extent_k`, то есть двумя полуплоскостями.
Ячейка = `clipHalfPlane(clipHalfPlane(rect, ...), ...)`, пустой результат пропускается.

Стартовый курсор сдвигается так, чтобы покрыть весь наклон:
`shearMm = t · |sSigned|`, обход начинается с первой полосы, чья верхняя граница ниже
`rowTop - shearMm`, и продолжается пока нижняя граница меньше `rowBottom + shearMm`.
При `s = 0` формула обязана давать в точности сегодняшний старт и сегодняшнюю нумерацию `k`
(инвариант 5). Проще всего: считать сегодняшний старт как сейчас, потом отмотать назад целое
число полос, покрывающее `shearMm`, и **сдвинуть нумерацию `k` на то же число назад**, чтобы
при `shearMm = 0` отмотка была нулевой.

Ячейка пишется как: `poly` из отсечения, `xMm/yMm/widthMm/heightMm` из `polygonBbox(poly)`,
и **если `sSigned === 0`, поле `poly` не пишется вовсе** и bbox считается по-старому. Это и есть
физическая гарантия инварианта 1.

Бюджет `MAX_CELLS` списывается по фактически выданным ячейкам, как сейчас.

**Тесты:**

- `lib/engine/compile.test.ts`: точечный кейс шеврона на двух колонках с `±30°`, проверка
  координат вершин руками посчитанных ячеек.
- `lib/engine/compile.sliceref.test.ts`: существующие кейсы не правятся, добавляются угловые.
- `lib/engine/compile.property.test.ts` (главное):
  - **регрессия нуля:** для случайного документа с нулевыми углами `JSON.stringify(compile(d))`
    равен эталону, снятому с текущего `main` (эталон снимается генератором фикстур в первой же
    итерации шага и коммитится);
  - **без дыр:** `Σ polygonAreaMm2(cellPolygon(c))` по ячейкам ряда равна
    `panelWidth · row.thicknessMm` с точностью `GEOM_EPS_MM`, для любого `φ ∈ [-60, 60]`;
  - **без наложений:** `polygonsOverlapMm2` любой пары ячеек ряда равна нулю;
  - **выпуклость и вложенность в габарит доски**;
  - **зеркальность:** `φ` и `-φ` дают одинаковые суммы площадей по породам;
  - **сцепка шеврона:** для документа, собранного по правилу `base_{k+1} = base_k + t_k · s_k`,
    вершины ячеек соседних колонок на общей границе совпадают с точностью `GEOM_EPS_MM`.

**Ловушки шага.**

- Деление `cycleMm` на `cos φ` забудут в 9 случаях из 10. Тест на конкретных числах обязателен.
- `row.mirror` переставляет элементы панели и обязан переворачивать знак наклона, иначе
  зеркальная доска будет ехать в ту же сторону. Тест: отражение модели по `x` при `mirror`.
  Если аналогичный тест при `φ = 0` красный уже сегодня, это существующий баг вне области
  задачи: зафиксировать в отчёте и ослабить тест до сравнения сумм площадей по породам.
- `row.flip` и `ref.flip` комбинируются через XOR, двойной флип это отсутствие флипа.

**Готово когда:** `pnpm vitest lib/engine` зелёный целиком.

### Шаг 1.5 `lib/engine/validate.ts`

**Что делается.**

- Снимается блокировка `ANGLE_UNSUPPORTED` на `SliceRef` (строка 121-123).
- Блокировка на `Row` остаётся, код меняется на `ANGLE_ROW_UNSUPPORTED` (строка 190-192).
- Новое, на каждый `SliceRef`:
  - `ANGLE_RANGE` (error), если `!Number.isFinite(angleDeg)` или `|angleDeg| > MAX_SLICE_ANGLE_DEG`;
  - `SLICE_TOO_SHORT` (error), если `sliceLengthMm(...) < panelLengthMm(design, outerPanelId)`:
    срез физически короче щита, в который вклеивается. Проверка существовала неявно и при
    `φ = 0`, угол делает срез длиннее, так что чаще будет ловить старые документы;
  - `ANGLE_WASTE` (warning) на панель, если `angledWasteMm2(panel)` даёт больше
    `ANGLE_WASTE_WARN_PCT` процентов площади щита. Это то самое место, за которое инструмент
    берут в руки: 30 градусов на щите 300 мм это 350 мм щита в отход, человек обязан это увидеть
    до того, как купит доску.
- `CELL_BUDGET` не трогается, но в отчёте шага зафиксировать замер: наклон меняет число ячеек
  в колонке (полосы длиннее в `1/cos`, но добавляется `t·|s|` перекрытия). Если на типовом
  шевроне число ячеек растёт больше чем на 20 процентов, сообщить оркестратору.

**Тесты:** `lib/engine/validate.test.ts` - правка кейса на строке 61, плюс: угол 75 градусов
ловится `ANGLE_RANGE`; угол 30 градусов на корректном документе не даёт ни одной ошибки;
`ANGLE_WASTE` появляется на большом угле и отсутствует на малом; `Row.angleDeg != 0` даёт
`ANGLE_ROW_UNSUPPORTED`.

## 3. Фаза 2. Потребители. Пять параллельных потоков

Стартуют одновременно после зелёной фазы 1. Общее правило для всех пяти: **старая ветка кода
для `cell.poly === undefined` остаётся дословно**, новая пишется рядом. Ни один существующий
тест не правится; если правится, это сигнал, что правило нарушено.

### Поток 2.1. 2D: экран и экспорт

**Файлы:** `components/BoardSvg.tsx`, `lib/export/svg.ts`, `components/promo/PatternCells.tsx`,
`components/BoardCanvas.tsx` (только проверка, что `closest('[data-cell]')` работает на

**Что делается.** Там, где `cell.poly` есть, вместо `<rect>` пишется
`<polygon points="...">`. Клеевой зазор: `insetConvex(cellPolygon(cell), gapMm / 2)` из
`geometry.ts` - для прямоугольника даёт ровно текущее поведение, поэтому старая ветка может быть
даже выражена через новую, если тесты остаются зелёными. Пустой результат `insetConvex`
(ячейка тоньше зазора) пропускается.

`lib/render2d/layout.ts` **не трогается**: доска остаётся прямоугольником (решение 0.2).

**Тесты:** `components/BoardSvg.test.tsx` - на угловой модели рендерится `polygon`, на прямой

**Готово когда:** `pnpm vitest components lib/export/svg` зелёный, ни один прежний ожидаемый
SVG не поменялся.

### Поток 2.2. 3D

**Файлы:** `lib/render3d/instances.ts`, `components/Board3D.tsx`, `components/Board3DPanel.tsx`.

**Что делается.** Инстансированные боксы теряются только там, где они и не годятся.
Стратегия с двумя путями:

- если ни у одной ячейки модели нет `poly`, работает **сегодняшний** путь `InstancedMesh`
  без единой правки (все существующие узоры, включая всю библиотеку шаблонов, идут сюда);
- если `poly` есть хотя бы у одной, `buildInstances` отдаёт вместо инстансов **одну слитую
  `BufferGeometry` на породу**: на каждую ячейку верхняя и нижняя грани веером треугольников
  плюс боковые квады, `jitter` переезжает из атрибута инстанса в атрибут вершинного цвета.
  4000 ячеек по 6 вершин это порядка 80 тысяч треугольников на всю сцену, для GPU это ничто,
  и потолок `MAX_INSTANCES` для этого пути становится неактуален.

`ExtrudeGeometry` не используется: он строит по одной геометрии на ячейку и даёт 4000 draw call.

Тип результата: дискриминированное объединение `{ kind: 'instanced', groups } | { kind: 'merged',
groups }`, чтобы компонент не гадал.

**Тесты:** `lib/render3d/instances.test.ts` - прямая модель даёт `kind: 'instanced'` и
побайтово прежний результат; угловая даёт `kind: 'merged'`, число вершин совпадает с суммой по
полигонам, суммарный объём слитой геометрии равен сумме площадей ячеек на толщину доски с
точностью `GEOM_EPS_MM` (это заодно вторая независимая проверка инварианта 2).

**Готово когда:** `pnpm vitest lib/render3d` зелёный и e2e `view3d.spec.ts` проходит.

**Это самый рискованный поток фазы 2.** Если слитая геометрия упирается в производительность
или в незнакомый API three.js, разрешено на время подставить bbox-боксы, но **сдавать так
нельзя**: 3D, показывающее прямоугольники там, где 2D показывает наклон, вскроется первым же
взглядом на демо. При срыве потока эскалировать оркестратору, а не сдавать компромисс.

### Поток 2.3. Расчёт материала и сводки

**Файлы:** `lib/calc/index.ts`, `lib/gallery/summary.ts`, `lib/promo/describe.ts`.

**Что делается.** Всюду, где сейчас `cell.widthMm * cell.heightMm`, ставится
`polygonAreaMm2(cellPolygon(cell))`. Правка на три строки, и это весь поток.

Отход считается сам: `rawVolumeMm3` строится через `panelLengthMm`, которое после шага 1.3 уже
включает и `1/cos`, и торцевые треугольники, а `finishedVolumeMm3` теперь честно меньше.
`wastePct` растёт без единой дополнительной строки.

**Тесты:** `lib/calc/index.test.ts` - на одном и том же узоре `wastePct` при `φ = 30°` заметно
выше, чем при `φ = 0` (конкретный порог зафиксировать по факту первого прогона, не выдумывать);

### Поток 2.4. Схема распила, PDF, CSV

**Файлы:** `lib/export/cutlist.ts`, `lib/export/pdf.ts`, `lib/export/csv.ts`,
ключи в `lib/i18n/ru.ts` и `lib/i18n/en.ts`.

**Что делается.** Это поток, ради которого вся затея: превью честно ровно настолько, насколько
честна схема.

- `Crosscut` получает `angleDeg`, `lengthMm` (`= sourceWidthMm / cos φ`).
- `SlicePiece` получает `angleDeg` и `flip`.
- `PanelCutPlan` получает `angledWasteMm2` и `endWasteMm` (длина торцевых клиньев вдоль щита).
- `CutPlan` получает `hasAngledCuts: boolean`.
- Шаги `buildGlueUpSteps`:
  - новый шаг `angled-setup` перед группой угловых резов: «выставить салазки на φ градусов,
    первый клин длиной X мм уходит в отход»;
  - шаг `crosscut` получает угловой вариант сообщения с длиной заготовки `W / cos φ`;
  - шаг `inlay` получает упоминание переворота, когда `flip = true`: «срез перевернуть перед
    вклейкой»;
  - в итогах панели появляется строка отхода на угол.
- CSV: колонки `angleDeg` и `lengthMm` в списке резов.
- PDF: те же данные, отдельная строка в блоке панели. Верстка `pdf.ts` работает по строкам
  текста, добавление безопасно.

**Тесты:** `lib/export/cutlist.test.ts` - угловой рез присутствует, `lengthMm` равен `W/cos φ`,
шаги содержат `angled-setup` и упоминание отхода; `lib/export/cutlist.property.test.ts` -
на любом документе число `angled-setup` равно числу различных ненулевых углов среди резов
панели; `lib/export/csv.test.ts` и `lib/export/purity.test.ts` без правок должны остаться
зелёными.

**Готово когда:** `pnpm vitest lib/export` зелёный, и **ручная сверка**: на демо-шевроне
сумма длин заготовок из cutlist плюс отход совпадает с `panelLengthMm` из `calc`. Это
единственное место, где расхождение движка и чертежа не поймает ни один тест, поэтому сверку
записать в отчёт числами.

### Поток 2.5. Персист, схема v3

**Файлы:** `lib/persist/schema.ts`, `lib/persist/codec.ts`.

**Что делается.**

- `sliceRefSchema` получает `flip: z.boolean().optional()`.
- `angleDeg` получает валидацию диапазона на уровне схемы **не строже** движка: любое конечное
  число принимается, диапазон это дело `validate`, а не парсера. Битый документ должен
  открываться с красной диагностикой, а не падать при чтении.
- `migrations[2] = (doc) => ({ ...doc, schemaVersion: 3 })`. Миграция тривиальна намеренно:
  отсутствующий `flip` эквивалентен `false`, отсутствующий `angleDeg` в старых документах
  невозможен (поле было в схеме с v1). Все сохранённые в Supabase проекты открываются без
  изменения смысла.
- `codec.ts`: компактная форма `SliceRef` получает шестой элемент `flip ? 1 : 0`. Читатель
  обязан переваривать массив из пяти элементов (`e[5] === undefined` -> `false`) - именно это
  делает старые ссылки и старый localStorage совместимыми.

**Почему всё-таки бамп до 3, если совместимость и так есть.** Версия это честная отметка
«документ из этой сборки может содержать угол». Она нужна поддержке и разбору жалоб, стоит три
строки и укладывается в уже существующий реестр миграций.

**Тесты:** `lib/persist/codec.test.ts` - документ с углом и флипом переживает круговой рейс
`serialize/deserialize` и `encodeDesignToHash/decode`; компактный массив из пяти элементов
читается как `flip: false`; `lib/persist/codec.property.test.ts` - круговой рейс на случайных
документах с углами.

Отдельный тест миграции на фикстурах: взять `lib/engine/fixtures.ts`, понизить `schemaVersion`
до 2, прогнать `parseDesign`, сравнить результат с исходным. Это и есть доказательство, что
проекты людей не пострадали.

**Готово когда:** `pnpm vitest lib/persist` зелёный и `pnpm tsc --noEmit` чистый по всему
проекту (кроме `lib/i18n`, который закроется шагом 3.4).

## 4. Фаза 3. Продукт

### Шаг 3.1 `lib/generators/angled.ts` (новый) и правки генома

**Файлы:** `lib/generators/angled.ts` (новый), `lib/generators/genome.ts`,
`lib/generators/families.ts`, `lib/generators/evolve.ts`.

**Что делается.**

`GenParams` получает `angleDeg: number`, `clampGenome` зажимает его в
`[-MAX_SLICE_ANGLE_DEG, MAX_SLICE_ANGLE_DEG]` и округляет до половины градуса.
`genomeKey` получает угол. `evolve.ts` учит мутацию угла.

`FamilyId` получает три значения в порядке приоритета:

1. **`chevron`** - панель P1 из мелких полос, панель P2 из `SliceRef` на P1 с чередующимся
   знаком угла и `offsetMm`, выведенным из правила сцепки `base_{k+1} = base_k + t_k · s_k`.
   Ряды прямые.
2. **`diamond`** - тот же chevron, но `mirror` чередуется по рядам: соседние ряды дают
   встречные V, из пары получается ромб. Стоит почти ничего поверх chevron.
3. **`tumbling`** - три породы, три угла в цикле, `offsetMm` по правилу трёх фаз. Дороже
   первых двух и делается последним.

`FAMILY_HINTS` для них: толщина среза `t` в коридоре 50-100 мм (см. раздел 0.5: амплитуда
зубца равна `t · tan φ`, из тонких срезов шеврон не читается), угол 20-40 градусов,
палитра 2-3 породы для chevron и diamond, ровно 3 для tumbling.

**Инвариант генератора, тот же, что и у остальных семейств:** после `clampGenome` документ
проходит `validate` без единой ошибки. Это единственная гарантия изготовимости во всём
генераторе, и `ANGLE_WASTE` как warning её не нарушает, а `ANGLE_RANGE` и `SLICE_TOO_SHORT`
нарушают - значит коридоры хинтов обязаны их исключать по построению.

**Тесты:** `lib/generators/angled.test.ts` - сцепка V на всех колонках; `families.property.test.ts`
и `purity.test.ts` расширяются на новые id без правки существующих кейсов;
`genome.test.ts` - угол переживает clamp и участвует в ключе.

**Готово когда:** `pnpm vitest lib/generators` зелёный, и на 200 случайных геномах каждого из

## 5. Карта рисков

| Риск | Где | Как ловим |
|---|---|---|
| Забытое деление `cycleMm` на `cos φ` | шаг 1.4 | точечный тест на посчитанных руками координатах, не на формуле |

живом шевроне, читаемость русских формулировок новых шагов инструкции, и визуальное качество
3D. Всё три идут в чеклист ручной проверки.

## 6. Что сознательно не делается

- **`Row.angleDeg`.** Угловой поперечный рез финального щита. Даёт скошенную доску, требует
  приведения параллелограмма к прямоугольнику, пересчёта габарита в `render2d/layout.ts`,
  двух дополнительных треугольников отхода и пересмотра `RAGGED_BOARD`. Отдача маленькая:
  все три целевых узора получаются без него. Остаётся заблокированным с честным текстом.
- **`flipRule` в документе.** Заменён явными числами в `SliceRef`, правило чередования живёт
  в генераторе.
- **Правка `render2d/layout.ts`.** Не нужна, пока доска прямоугольник.
- **Проверка минимальной полосы по нормали к резу.** Геометрически совпадает с существующей
  `MIN_STRIP_WIDTH`.
- **Отдельная работа по PNG и OG-картинкам.** Они строятся поверх `lib/export/svg.ts` и
  получат полигоны бесплатно вместе с потоком 2.1.
- **`tumbling blocks`, если время кончается.** Chevron и diamond закрывают обещание «угловые
  узоры»; tumbling это третий узор того же класса, его отсутствие не делает фичу нечестной.
  Порядок в шаге 3.1 выставлен так, чтобы обрезать по этой границе.

## 7. Порядок выдачи агентам

```
фаза 1 (последовательно):   1.1 -> 1.2 -> 1.3 -> 1.4 -> 1.5
фаза 2 (параллельно):       2.1 | 2.2 | 2.3 | 2.4 | 2.5
фаза 3:                     3.1 -> 3.2, параллельно 3.3 | 3.4, затем 3.5
```

Между фазами оркестратор прогоняет `pnpm tsc --noEmit && pnpm vitest run` целиком и не
запускает следующую фазу на красном. Модель для всех шагов `sonnet`; ревью шагов 1.4 и 2.4
делает `opus`, потому что там ошибка не видна в тестах.
